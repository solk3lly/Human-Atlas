## 2. Indonesian (EYD V / KBBI VI) & English (TA2) Terminology Standards

To prevent mixing orthographic rules with stylistic preferences, every terminology decision below explicitly distinguishes:
1. **Kaidah Ejaan (EYD V)** — mandatory spelling rule from *EYD Edisi V (2022)*;
2. **Bentuk Baku (KBBI VI)** — canonical dictionary lemma;
3. **Konvensi Terminologi Anatomi (TA2 / PAAI / Sobotta EGC)** — domain nomenclature;
4. **Pilihan Editorial** — project-wide consistency rule (e.g., preserving machine keys like `BL.urin` while fixing human-facing Indonesian labels).

### 2.2 Special Terminology Verification: `Bucinator` vs `Buccinator` (TA2 ID `2086`)

Primary-source verification against **FIPAT TA2** (TA2 ID `2086`, TA98 `A04.1.03.036`) and Z-Anatomy's `TA2.csv` line `2086` resolves an important subtlety:
- **Official TA2 Latin (`l`):** `Musculus bucinator` *(one `c`, from Classical Latin* *bucina* "trumpet"; *Musculus buccinatorius* is listed as a Latin variant).*
- **Official TA2 English (`e`):** `Buccinator muscle` *(two `c`s).*
- **Standard Indonesian (`n`, Dorland / Sobotta EGC / EYD V):** `Otot Buksinator`.
- **Current bug in `BL['otot']`:** `{"id": "Bucinator", "n": "Bucinator", "l": "", "e": "Bucinator"}` — exposes raw Latin-only spelling as both the Indonesian name and English subtitle while leaving `l` blank.
- **Correct remediation:** Keep `id: "Bucinator"` (matching the Z-Anatomy mesh base name `Bucinator.r/.l` unless remapped), set **`n: "Otot Buksinator"`**, **`l: "Musculus bucinator"`**, **`e: "Buccinator muscle"`**!

## 4. 3D Asset, Geometry, and Viewer Engineering Remediation Analysis

### 4.1 Z-Anatomy Muscles (`otot`): Root Cause of 80 Enthesis-Only Muscles & 32 L/R Swaps

- **Enthesis selection bug (`tools/cls.py:21–24`):**
  ```python
  for want in 'epo':
      w = [x for x in v if x[4] == want]
      if w: keep += w; break
  ```
  In Z-Anatomy's naming convention (`split()` at `tools/cls.py:4–9`), suffix `.r`/`.l` (`t == 'p'`) denotes the **actual 3D muscle belly**, `.er`/`.el` (`t == 'e'`) denotes the **insertion enthesis bone-attachment sticker**, and `.or`/`.ol` (`t == 'o'`) denotes the **origin bone-attachment sticker**. Iterating `'epo'` deliberately threw away `'p'` whenever an `'e'` patch existed, wiping out **80 of 211 muscles** (76 `.e*`-only, 4 `.o*`-only; 317/591 meshes).
- **Required fix for `tools/cls.py`:** Change priority strictly to **`'p'` only** for muscle bellies (`[x for x in v if x[4] == 'p']`), explicitly excluding `.e*` and `.o*` enthesis/origin bone stickers from `otot` (or only falling back if a muscle genuinely lacks `'p'` after manual audit — never silently keeping 25 mm bone dots as Biceps brachii).
- **32 left/right swapped `.el`/`.er` meshes & swapped Trapezius:** In Z-Anatomy's anatomical coordinate frame (`+X` = anatomical left, `-X` = anatomical right), 32 `.el`/`.er` meshes carry inverted X-polarity, and `Ascending_part_of_trapezius_muscle` vs `Descending_part_of_trapezius_muscle` have swapped cranial-caudal `Y` coordinates (`Y = 1.57 m` occipital vs `Y = 1.12–1.41 m` lower thoracic). Re-extraction MUST include an automated **geometric polarity validator**: for every paired `.l`/`.r` mesh with `|centroid.x| > 10 mm`, assert `centroid(mesh.l).x > 0` and `centroid(mesh.r).x < 0`, plus vertical ordering checks for multi-part muscles (`Descending_part_of_trapezius` centroid Y > `Transverse` > `Ascending`).

### 4.3 Viewer Camera (`cam.near`), Mobile Reflow (WCAG 1.4.10), and Dark-Mode Contrast (WCAG 1.4.3)

1. **Dynamic `cam.near` & `ctl.minDistance` math (`index.html:820–847`):**
   - Perspective depth buffer resolution is non-linear and strongly coupled to the `far / near` ratio (`Three.js` `PerspectiveCamera` docs). Setting a globally tiny `near` (e.g., `1e-5` with `far = 100`, ratio `10^7`) causes z-fighting on full-body views (`rangka`).
   - Instead, couple **both** `cam.near` and `cam.far` dynamically to `focusRadius` inside `updateFocusDistance()`:
     ```js
     cam.near = Math.min(0.003, Math.max(focusRadius * 0.02, 1e-4));
     cam.far  = Math.max(100, focusRadius * 200);
     cam.updateProjectionMatrix();
     ctl.minDistance = Math.max(focusRadius * 0.3, cam.near * 2.5);
     ```
   - Verification on edge cases:
     - **Full skeleton** (`focusRadius ≈ 0.90 m`): `near = 0.003 m`, `far = 180 m` (ratio `6×10^4`, identical depth precision to today), `minDistance = 0.27 m`.
     - **Single `Corniculate_cartilage`** (`focusRadius = 1.35 mm`): `near = 0.0001 m` (`0.10 mm`), `far = 100 m` (or better: `far = Math.max(20, dist * 20)` so ratio stays `≤ 2×10^5`!), `minDistance = 0.405 mm > 2.5 × 0.10 mm`. At minimum zoom, the mesh surface sits well in front of `cam.near` — **zero near-plane clipping and zero depth-buffer degradation**.
   - Note: `cam.far = Math.max(focusRadius * 40, dist * 10, 5)` keeps the `far / near` ratio bounded (`≤ 5×10^4`) even on microscopic lymph node (`focusRadius ≈ 9 mm`) and ossicles (`Stapes`, `focusRadius = 2.8 mm`)! Let's ensure `cam.far` always exceeds the whole-layer bounding sphere diameter (`>= Math.max(layerSpan * 4, dist * 6, 5)`) so faded non-selected context meshes in `Sorot` mode are never clipped at the far plane.
2. **Hover raycasting threshold (`index.html:1495`):**
   - Disabling hover at `MESH[layer].length > 150` breaks hover on `rangka` (277 meshes, 329k tris), `otot` (591 meshes, 266k tris), and `saraf` (237 meshes, 78k tris) while leaving it ON for `vsTo` (590k tris) and `vsTu` (536k tris).
   - Better design: gate hover by **total visible triangle budget** (or pre-test `Ray.intersectsSphere(mesh.geometry.boundingSphere)` before triangle intersection, plus adaptive throttle: `90 ms` when `< 400k` tris, `160 ms` when `400k–900k` tris, disable only above `1.1M` tris like `vsKa`'s 1.3M tris — OR run coarse bounding-sphere filter so even `vsKa` hits only 1–3 candidate meshes per pointer move!). Bounding-sphere pre-filtering in `hit(e)` reduces per-frame raycast cost by 50–100× on multi-mesh layers (`rangka`, `otot`, `saraf`) AND lets us keep hover enabled on `rangka`, `otot`, `saraf`, and all organ layers!
   - Clamp `#tip` coordinates inside `#vw` bounds (`left = cl(x + 14, 6, vwW - tipW - 6)`, `top = cl(y + 14, 6, vwH - tipH - 6)`, flipping above/left of cursor if near bottom/right edge).
3. **Mobile layout (`≤ 760 px` & `320×568` WCAG 1.4.10 Reflow):**
   - Root cause of `#list` collapsing to `0 px` and `body` overflowing vertically: `#side` (`height: var(--sh, 30%)`), `#vw` (`min-height: 185px`), and `#dsc` (`#info { height: 34dvh }` + `#ihd`) independently sum to `> 100dvh`, while `#side`'s chrome (`#hd`, `#ttl`, `#tabs`, `#sys`, `#q`) consumes `~210 px`.
   - Fix: On `@media (max-width: 760px)`:
     - Make `#side` collapsible/drawer-friendly or default to **collapsed (`sc`) on initial mobile load OR compact chrome** (hide verbose `#ttl` on `≤ 760 px`, compact `#hd`/`#tabs`/`#sys`/`#q` padding so chrome is `≤ 115 px`, set default mobile `#side` height to `clamp(170px, 34dvh, 240px)` with `#list { min-height: 56px; overflow-y: auto }`), AND set `#main { flex: 1; min-height: 0; display: flex; flex-direction: column }`, `#vw { flex: 1 1 0; min-height: 160px }`, `#dsc { flex: none }`, `#info { height: var(--ih, 24dvh); max-height: 45dvh }` (auto-clamped on resize so `#side + #vw + #dsc <= 100dvh` with **zero vertical clipping** even at `320×568`!).
     - Move `#ctl` on mobile into a dedicated top-row strip (part of `#vw`'s CSS grid: `grid-template-rows: auto minmax(0, 1fr) auto` with `#sbt` + `#ctl` in Row 1, `<canvas id="cv">` in Row 2, `#bar` in Row 3!) so camera buttons **never overlap the 3D skull or great vessels**!
4. **Dark-mode `color-scheme` & WCAG 2.2 SC 1.4.3 link contrast (`≥ 4.5:1`):**
